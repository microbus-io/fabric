# Agentic Workflows

Agentic workflows allow microservices to collaborate on multi-step processes. A workflow is a directed graph of tasks orchestrated by the Foreman core service. Each task is a standalone endpoint that reads from and writes to a shared state carried by a `*workflow.Flow`.

## Vocabulary

In this codebase, **"workflow", "agent", and "agentic workflow" all refer to the same thing**: a `workflow.Graph` of tasks orchestrated by the Foreman. The everything in this file applies whether the workflow is rule-based and deterministic, driven by a small specialized model, or built around `llmapi.ChatLoop` and a frontier LLM. An LLM call is *not* a prerequisite for a workflow to be an agent - an agent is autonomous software that perceives state, decides, and acts toward a goal, and a Microbus workflow satisfies that definition regardless of which task types it contains.

So when a user says "create an agent", "create an agentic workflow", or "create a workflow", treat them as the same request and use the `add-workflow` skill. The same applies to "agent step" / "workflow step" / "agentic task" - all map to a single task endpoint and the `add-task` skill. The presence or absence of an LLM-driven task does not change which skill to use, which conventions apply, or which file structure to produce.

A microservice whose sole reason for existing is to expose one workflow is built and registered exactly like any other Microbus microservice. Its hostname follows the same domain-oriented naming as every other host (e.g. `planner.security.acme`); do not encode the fact that a host is an agent into its hostname. If an author wants to hint the role, that belongs in the author's choice of leaf segment, not in a framework-prescribed suffix.

## Task Endpoints

A task endpoint is a functional endpoint that performs a single step of a workflow. Its signature always includes `ctx context.Context` and `flow *workflow.Flow` as the first two parameters, followed by input arguments sourced from the flow's state, and returns output arguments written back to the state plus `err error`.

```go
import "github.com/microbus-io/dwarf/workflow"

func (svc *Service) VerifyCredit(ctx context.Context, flow *workflow.Flow, creditScore int) (creditVerified bool, err error) {
	if creditScore >= 700 {
		return true, nil
	}
	return false, nil
}
```

A task's input and output arguments are a **declaration of the state variables it uses**: an input argument names a state var the task reads, and an output argument names a state var the task writes back. Input arguments are matched by name to fields in the flow's state; output arguments are written back to the state under their name (through the marshaler, and through the graph's reducer for that key if one is set, exactly as an equivalent `flow.Set` would be). **Any value a task returns without an error is applied to the state** - through the field's reducer, or the default `Replace` when it has none - on every successful return, including a park's `yield` path. A zero value is applied like any other: under `Replace` it replaces the field (nil deletes it), and under some reducers it just happens to change nothing (nil under any reducer, `0` under `Add`, `false` under `Or`). An error return applies nothing. Returned values are applied after the task body, so a returned value overwrites an earlier `flow.Set` of the same field simply by running later; do not both `flow.Set` a field and return it as an output - use one or the other. An output argument with an `Out` suffix (e.g. `creditScoreOut`) implements a read-modify-write pattern - it appears as both input and output. On a reduced field, the pair carries a contribution, not the new total (see Reducers below).

**Reading a state var as an input never consumes it.** A state var stays in the flow's state after a task reads it; declaring it as an input just gives the task a typed view of it. The same var remains available to other tasks and to graph machinery - e.g. a task can take `pendingToolCalls` as an input while a `forEach` transition on the same node still iterates that state key. To actually remove a state var, a task must `flow.Del` it (or `flow.Clear` it); declaring it as an input does not.

A task need not have any outputs. A pure side-effect step (restart a node, attach a file, set a status, then `flow.Goto`) returns only `err error`, and its generated `Out` struct is an empty `struct{}`. That is valid and idiomatic - such a task contributes no state fields and routes purely by side effect, `flow.Goto`, or a downstream `Switch`/`When` reading state set by other tasks.

**Prefer typed arguments over `flow.Get`/`flow.Set`.** Task inputs and outputs should be expressed as typed function arguments wherever the types are available in the API package. This makes the task's state contract explicit in the signature and lets the marshaler handle serialization. Reserve `flow.Get`/`flow.Set` only for internal types that are not part of the public API (e.g. intermediate state shared between tasks within the same microservice).

```go
// Typed arguments make the state contract explicit
func (svc *Service) ProcessResponse(ctx context.Context, flow *workflow.Flow, llmContent string, toolRounds int) (toolsRequested bool, toolRoundsOut int, err error) {
    // llmContent and toolRounds are read from state automatically
    // toolsRequested and toolRoundsOut are written back to state automatically
}
```

Tasks are registered on port `:428` by default.

## Workflow Graph Endpoints

A workflow graph endpoint returns a `*workflow.Graph` that defines the structure of a workflow - its tasks, transitions, and merge strategies. The graph is fetched once when a flow is created and stored with it.

**Naming convention: graph names and task (node) names are PascalCase** (`CreditApproval`, `VerifyCredit`) - they are graph-topology identifiers, kept visually distinct from the lowercased dispatch URLs the nodes resolve to (`myserviceapi.VerifyCredit.URL()`) and the camelCase state field names (`creditVerified`). `SetURL(name, url)` registers a node under a PascalCase name that resolves to the task's URL; every transition, `SetFanIn`, and `flow.Goto` then refers to that PascalCase node name, never the URL. The first node bound with `SetURL` is the entry point unless `SetEntryPoint` names another. The name passed to `NewGraph` is a display label; the graph carries no URL of its own, since the foreman is handed the workflow's URL separately (`Run`, `Create`).

```go
import "github.com/microbus-io/dwarf/workflow"

func (svc *Service) CreditApproval(ctx context.Context) (graph *workflow.Graph, err error) {
	graph = workflow.NewGraph("CreditApproval")
	// SetURL(PascalCaseNodeName, dispatchURL): the node name is the graph identifier; the URL is where it runs.
	graph.SetURL("SubmitApplication", myserviceapi.SubmitApplication.URL())
	graph.SetURL("VerifyCredit", myserviceapi.VerifyCredit.URL())
	graph.SetURL("VerifyEmployment", myserviceapi.VerifyEmployment.URL())
	graph.SetURL("FinalDecision", myserviceapi.FinalDecision.URL())

	// Fan-out: SubmitApplication has two normal outgoing transitions, so VerifyCredit and VerifyEmployment run as parallel branches
	graph.AddTransition("SubmitApplication", "VerifyCredit")
	graph.AddTransition("SubmitApplication", "VerifyEmployment")
	// Fan-in: every parallel branch must converge on a node marked with SetFanIn, or graph.Validate rejects the graph
	graph.SetFanIn("FinalDecision")
	graph.AddTransition("VerifyCredit", "FinalDecision")
	graph.AddTransition("VerifyEmployment", "FinalDecision")
	// Conditional transition: the when expression references a state field, which stays camelCase
	graph.AddTransitionWhen("FinalDecision", workflow.End, "creditVerified")
	// Goto transition (taken only when the task calls flow.Goto), targeting a PascalCase node name
	graph.AddTransitionGoto("FinalDecision", "SubmitApplication")

	return graph, nil
}
```

Task URLs in the graph are obtained from the generated API package constants (e.g. `myserviceapi.TaskName.URL()`); the node names you pass alongside them are PascalCase labels you choose (conventionally matching the task's name).

## Reducers

**Reducers** control how writes to a state field combine. A write to a field with a reducer is a **contribution**, folded through the reducer at every hand-off: the next step, the fan-in, the final state and `Continue`. A read returns the combined value. Every field that needs anything other than last-write-wins must be wired explicitly with `graph.SetReducer(field, reducer)` at graph-build time. Fields without a registered reducer use `Replace` (last write wins). State field names carry no hidden semantics - name them naturally (e.g. `messages`, `total`, `tags`) and attach the reducer separately.

```go
graph.SetReducer("messages", workflow.ReducerAppend)  // accumulate each write's elements
graph.SetReducer("total",    workflow.ReducerAdd)     // sum numeric contributions
graph.SetReducer("seen",     workflow.ReducerUnion)   // dedupe across branches
graph.SetReducer("approved", workflow.ReducerAnd)     // all branches must approve
graph.SetReducer("flagged",  workflow.ReducerOr)      // any branch flags
graph.SetReducer("notes",    workflow.ReducerConcat)  // join string contributions
graph.SetReducer("attrs",    workflow.ReducerMerge)   // merge per-branch objects
```

The supported reducer values:

- `workflow.ReducerReplace` - last write wins (default)
- `workflow.ReducerAppend` - concatenate arrays
- `workflow.ReducerAdd` - sum numeric values
- `workflow.ReducerMin` - keep the smaller numeric value
- `workflow.ReducerMax` - keep the larger numeric value
- `workflow.ReducerUnion` - merge arrays, deduplicate by JSON value (numbers compare by value)
- `workflow.ReducerMerge` - merge objects, new key wins on collision
- `workflow.ReducerAnd` - logical AND of booleans
- `workflow.ReducerOr` - logical OR of booleans
- `workflow.ReducerConcat` - concatenate strings

Reducers are strict on their input type: `Add`, `Min` and `Max` take numbers, `Merge` takes an object, `And` and `Or` take booleans, `Concat` takes strings, and `Append` and `Union` take either a list or a single element (`Union` deduplicates by value, objects included). A nil (JSON null) is the only value that contributes nothing under every reducer. A zero value is folded like any other: `0` changes nothing under `Add` but competes like any other number under `Min`, and `false` changes nothing under `Or` but makes `And` false.

**Empty-cohort behavior.** A `forEach` that spawns zero branches still fires the fan-in, which runs on the source task's own state with no branch contributions, so a reduced field keeps its incoming value (absent if nothing wrote it). There is no "vacuously true" `ReducerAnd`: if an empty cohort must count as approval, branch on the cohort size downstream rather than relying on the reducer.

**Order.** `Append` (arrays) and `Concat` (strings) combine a cohort's contributions in branch order - for a `forEach`, the order of the input array - not in the order the branches complete, so the result is deterministic.

**Contributions, not totals.** The result of a reduced field does not depend on the graph's shape, so the same rules apply in a straight line, in a fan-out branch and at a fan-in:

- **Write your contribution, not the value you read.** With `messages` on `ReducerAppend`, `flow.Set("messages", []llmapi.Item{reply})` adds the reply. `flow.Set("messages", append(history, reply))` adds the whole history again. Likewise a `VerifyEmployment` task running once per employer with `graph.SetReducer("failures", workflow.ReducerAdd)` returns `failuresOut` of 0 or 1 (its own count), not the running total.
- **`Overwrite` to trim or reset a reduced field.** `flow.Overwrite("messages", history[max(0, len(history)-20):])` keeps the last 20, and later writes in the same task add to the new value. `Overwrite` returns an error inside a fan-out branch, and a `Del` or `Clear` of a reduced field there fails the step: reset the field before the fan-out or after its fan-in.
- **Contribute after `Interrupt` or `Subgraph`.** A step's runs compose: after a `Retry`, a `Resume` of an `Interrupt`, or a `Subgraph` returning, the task runs from the top again and each run's contributions add to the earlier runs'. A contribution made before the park is made twice.
- **A subgraph returns only what it adds.** Writing a child's result into a reduced field of the parent is a contribution like any other, so have the child return its new elements, not the history it was given.

**`Out` pairs on a reduced field.** The `items` in, `itemsOut` out pair invites read-modify-write, which is wrong on a reduced field. Return only the contribution: `itemsOut = append(items, reply)` adds the history again, and so does a pass-through branch such as `if nothingToDo { return items }`. On a path that should add nothing, including the `yield` path of a park, return a value that changes nothing under the field's reducer, such as nil for a list. On a field with no reducer the pair stays a plain read-modify-write, and a park's `yield` path returns the input unchanged so the park does not overwrite it.

## Fan-Out and Fan-In

A **fan-out** is any node with two or more normal outgoing transitions, or any `forEach` transition. Goto-only and
error transitions do not count toward fan-out. When a node fans out, the branches it spawns run in parallel, and they
must all converge on a single node that you explicitly mark with `graph.SetFanIn(name)`.

This is mandatory, not optional. `graph.Validate` (called by the workflow's marshaler before the foreman runs the
graph) rejects:

- A fan-out source with no downstream `SetFanIn` node ("fan-out source ... has no fan-in node downstream").
- A path that reaches `workflow.End` while parallel branches are still open ("transition to END ... has unpopped
  fan-out frames").

A graph that fans out but never calls `SetFanIn` compiles and passes `go vet` - it fails only at run time when the
foreman fetches and validates the graph. Adding the fan-out without the matching fan-in is the single most common way
to produce an invalid graph, so add the `SetFanIn` call in the same edit as the fan-out transitions.

```go
graph.SetURL("Split", myserviceapi.Split.URL())
graph.SetURL("BranchA", myserviceapi.BranchA.URL())
graph.SetURL("BranchB", myserviceapi.BranchB.URL())
graph.SetURL("Join", myserviceapi.Join.URL())
graph.SetFanIn("Join")                  // mark the convergence node
graph.AddTransition("Split", "BranchA") // fan-out: two normal edges
graph.AddTransition("Split", "BranchB")
graph.AddTransition("BranchA", "Join")  // every branch converges on the fan-in node
graph.AddTransition("BranchB", "Join")
graph.AddTransition("Join", workflow.End)
```

The same rule applies to a `forEach` fan-out: `graph.AddTransitionForEach("Split", "Worker", "items", "item")` followed
by `graph.AddTransition("Worker", "Join")` and `graph.SetFanIn("Join")` (node names PascalCase; `items`/`item` are state fields). An empty `items` array spawns zero branches;
the foreman then creates the fan-in step directly, so the flow still continues past the join.

State fields produced by the parallel branches are merged at the fan-in node by reducers (see Reducers above). Attach
the appropriate reducer at graph-build time with `graph.SetReducer(field, reducer)`. Each branch writes only its own
contribution, never the accumulated value.

### `forEach` Branch State

A `forEach` branch sees the flow's state as it was at the fan-out, including the source array. The array is stored
once and shared by every branch rather than copied into each, so a large array costs no more per branch than a small
one. Each branch also gets two read-only fields, named after the `as` alias:

- `<as>Index` (`int`) - this element's 0-based position in the `forEach` array.
- `<as>Count` (`int`) - the cohort size (total elements in the `forEach` array).

For `AddTransitionForEach("Split", "Worker", "items", "item")` the branch sees `item`, `itemIndex`, `itemCount`.
A task argument by that name (e.g. `func Worker(... item string, itemIndex int, itemCount int)`) is auto-populated
from state like any other. These fields are present only for `forEach` fan-out, not static fan-out.

`<as>`, `<as>Index`, and `<as>Count` are **dropped from the merged state at fan-in**. They are per-element bookkeeping with no meaning past the cohort, so the foreman
deletes them after merging the cohort's contributions. A workflow that needs the element value past the fan-in
must forward it under a different key in the branch (e.g. `flow.SetString("chosenItem", item)`); the `as` alias
itself is gone downstream of the fan-in.

To suppress the source array past the fan-in (useful when it is very large and only the per-element transformation
matters downstream), have the branch call `flow.Set("<forEach>", nil)` in its task body. That writes the new value
into the branch's `changes`, the replace reducer folds it over the spawn-step base at fan-in, and the field is
absent (or whatever the branch wrote) past the join.

To reuse one task at two graph positions across a fan-in boundary (for example, fan in and then loop back), register
the same task URL under two distinct names with `SetURL`; each name is a separate node with its own lineage scope. See
`exampleservices/creditflow/service.go` for a worked graph that combines fan-out/fan-in, `forEach`, subgraphs, goto loops, and
error transitions.

## Switch Transitions

`AddTransitionSwitch(from, to, when)` declares a first-match-wins outgoing transition. When the source task finishes, the foreman walks the source's `Switch` transitions in declaration order, evaluates each `when` expression against the post-task state, and follows the **first** one that matches. The remaining `Switch` transitions are skipped on that step. Because exactly one branch ever fires, the downstream branches do **not** need to converge on a `SetFanIn` node.

```go
graph.SetURL("Router", myserviceapi.Router.URL())
graph.SetURL("HighValue", myserviceapi.HighValue.URL())
graph.SetURL("MidValue", myserviceapi.MidValue.URL())
graph.SetURL("LowValue", myserviceapi.LowValue.URL())
graph.AddTransitionSwitch("Router", "HighValue", "amount >= 10000")
graph.AddTransitionSwitch("Router", "MidValue", "amount >= 1000")
graph.AddTransitionSwitch("Router", "LowValue", "true") // default branch
graph.AddTransition("HighValue", workflow.End)
graph.AddTransition("MidValue", workflow.End)
graph.AddTransition("LowValue", workflow.End)
```

Rules the validator enforces:

- `when` is required on every `Switch` transition. Use `"true"` for the default catch-all.
- A node that uses `Switch` must declare **every** success-path outgoing transition as `Switch`. Mixing `Switch` with `When`, plain `AddTransition`, `AddTransitionForEach`, or `AddTransitionGoto` from the same source is rejected. `AddTransitionOnError` stays allowed because they live on a different axis (error vs. success).
- A `Switch` transition cannot also be a `forEach`, `Goto` or `OnError` transition: each transition is one kind.

If no `Switch` matches at runtime, the flow ends at the source node (no successor is created, the source step completes, and the flow transitions to `completed` via the normal "no next steps" path). To make termination explicit, target `workflow.End` from a final `Switch` with a tail predicate.

### When to choose Switch vs. When vs. Goto

Prefer in this order:

1. **`AddTransitionSwitch`** for any routing where you want exactly one branch to run based on data the graph can see. It's the safest of the three: the validator guarantees mutual exclusivity (so two siblings can't accidentally both fire and leak a parallel branch), there's no `SetFanIn` to forget downstream, and the Mermaid diagram labels each arm with its predicate. The cost is rigidity: every success-path edge from the source must be `Switch` once any of them is, so you commit the whole node to switch-style routing.
2. **`AddTransitionWhen`** when the source genuinely **does** fan out under multiple matching conditions, or when one of the siblings is unconditional and represents a "do this in addition to" branch. `When` predicates are evaluated independently and any number of them can match - that's the right semantic for parallel work, the wrong one for routing. If you're writing two `AddTransitionWhen` calls whose predicates are intended to be mutually exclusive (`x>0` and `x<=0`), convert them to `Switch` so the validator enforces what you meant; non-exclusive `When` predicates are a footgun (both fire, you suddenly need `SetFanIn`).
3. **`AddTransitionGoto`** only for runtime control-flow decisions the task body makes - loop-back from a fan-in node, "ask for more input then retry", LLM tool loops. `Goto` is invisible to the graph's structural rules (no lineage push/pop), so reach for it only when the branching condition is not a function of state that the graph could evaluate.

In short: `Switch` is the default for branching. Use `When` only for genuine fan-out, `Goto` only when the task body must decide at runtime.

## Error Transitions

Error transitions route task failures to an error handler instead of failing the flow. When the source task returns an error, the foreman serializes it as a `*errors.TracedError` (with stack trace, status code, and properties) into the `onErr` state field and dispatches the error handler task. An error transition takes no condition and cannot be a `forEach` or `Goto` transition. If the task was in a fan-out, all siblings are cancelled.

The error handler task must include `onErr *errors.TracedError` as an input parameter:

```go
func (svc *Service) HandleMyError(ctx context.Context, flow *workflow.Flow, onErr *errors.TracedError) (result bool, err error) {
    svc.LogWarn(ctx, "Handling error", "error", onErr)
    // Remediation logic...
    return false, nil
}
```

If the error handler itself returns an error, the flow fails normally.

## Subgraphs and Interrupts

A **subgraph** is a child *workflow* launched from inside a task body via `flow.Subgraph(workflowURL, in, &out)`. The parent step parks while the child runs and re-enters the task once the child terminates. **This is the only correct way for one task to invoke another unit of work with state isolation - do not call `foremanapi.NewClient(svc).Run`, nor the test-only `Executor`, from a task body; that spawns an independent flow (or a foreman-coupled call) and forfeits re-entry, single-flow audit trail, cascading cancellation, and interrupt propagation.**

A bare *task* is not an independently invocable unit - it is only ever a node in a graph. To invoke a single unit of work in isolation, declare a one-node workflow and subgraph it.

**Two ways to compose tasks, by state exposure.** Inside a flow you reach task B either by **graph composition** (B is a node in the same graph: it sees and writes the parent's *full* state - tightest coupling) or by a **subgraph** (B is a separate workflow run as an isolated child: only the explicit `in` crosses in, only the explicit `out` crosses back). Use graph composition when B is a genuine step of this workflow sharing its state vocabulary; use a subgraph when B is a reusable or foreign workflow you invoke with explicit arguments and don't want to hand your whole state to.

**A subgraph is a function call.** Only the explicit `in` crosses into the child as its initial state, and only the explicit `out` (the child's final state, unmarshaled into your pointer by JSON tag) crosses back. The parent's state is NOT inherited in either direction. `nil` input means "no arguments". A caller that wants the parent's full state to cross passes `flow.Snapshot()` (or a derived map) as `in`.

**Prefer the typed client over the raw primitive.** The generated `xapi.NewSubgraph(flow)` client wraps `flow.Subgraph` with typed In/Out: `out1, yield, err := otherapi.NewSubgraph(flow).SomeWorkflow(ctx, args...)`. Reach for the raw `flow.Subgraph` only for dynamic/untyped dispatch (a computed URL, or a service whose `*api` package you don't import).

### The park-and-resume pattern

`flow.Subgraph` and `flow.Interrupt` share one shape: park-the-step now, return the resolved value on re-entry. The result is unmarshaled into a trailing `out` pointer (`*struct` for type safety, `*map[string]any` for dynamic access, or `nil` to ignore); the call returns only `(yield, err)`.

```go
// Subgraph: embed a whole child workflow.
var out SomeOut // or: var out map[string]any
yield, err := flow.Subgraph(otherapi.SomeWorkflow.URL(), SomeIn{Field: "value"}, &out)
if yield {
    return nil          // first pass: parked, child running
}
if err != nil {
    // Child failed. The task may inspect err and retry, route, or propagate.
    if errors.StatusCode(err) == http.StatusRequestTimeout && flow.Retry(time.Second, 2.0, 30*time.Second, 5*time.Minute) {
        return nil      // re-arms a fresh child on re-dispatch
    }
    return errors.Trace(err)
}
// Resolved + succeeded: adopt the fields the parent wants from out into its own state.
flow.SetString("parentResult", out.Field)
return nil
```

`flow.Interrupt` is symmetric (its `out` carries the `Resume` payload):

```go
var resume map[string]any
yield, err := flow.Interrupt(map[string]any{"request": "userInput"}, &resume)
if err != nil {
    return errors.Trace(err)
}
if yield {
    return nil          // first pass: parked, waiting for Resume
}
// resume carries the Resume payload
```

| | `flow.Interrupt()` | `flow.Subgraph()` |
|---|---|---|
| **Signal** | Park, wait for external `Resume` | Park, wait for child workflow |
| **Foreman** | Parks the step | Parks the step and launches the child |
| **On completion** | `Resume(flowKey, data)` re-dispatches the step | The child's terminal outcome re-dispatches the step |
| **Re-entry signal** | `yield=false`, the Resume payload in `&resume` | `yield=false`, the child's final state in `&out` (success) or its failure as `err` |
| **Failure mode** | No child to fail; `err` only for a payload that does not marshal, resume data that does not unmarshal into `&resume`, or a second park in the step | Child failure delivered to parent as `err`; parent decides retry/route/propagate |

**Re-entry is signaled by the parker's `yield` bool, not by a state field.** Do not invent a `*Out`-suffix flag or a "have I run before" arg - the engine already tracks it and surfaces it as `yield`. The `if yield { return nil }` line is the **before-resume region** and runs on every dispatch (first pass, re-entry, every retry attempt); everything after it is the **after-resume region** and runs once per resolution. Exactly-once side effects (firing an event, charging a card) belong after the guard.

**State written before the park survives the park.** A `flow.Set*` / `flow.Del` made in the same dispatch *before* calling `flow.Interrupt` (or `flow.Subgraph`) is recorded in the step's `changes` and persisted when the step parks, so it is visible as an input on re-entry and to downstream tasks. This is the basis for idempotent side-effecting parks: a task that creates an external resource, records its identifier with `flow.SetString`, and then parks reads that identifier back on re-entry and skips re-creating the resource (e.g. `if id == "" { id = create(); flow.SetString("id", id) }; flow.Interrupt(...)`). Persisting through the change set is what makes this work - a plain local variable would *not* survive the park. Output args returned on `yield` are applied as well, after the body, so keep a field the body sets with `flow.Set*` out of the task's outputs: the returned value would overwrite it.

**Returning an error commits nothing - a failed step is atomic.** The generated handler is `out.X, err = svc.Task(...); if err != nil { return err }; err = flow.Set("x", &out.X); ...; encode(flow)`. When the task returns a non-nil `err`, the handler returns *before* both the `flow.Set` of each output arg and the flow re-encoding, so **neither the output args nor any `flow.Set`/`flow.Del` the task made in that dispatch reach the foreman** - the step fails, the pre-step state is kept intact, and routing goes to `OnError` if wired. A returned zero value (e.g. `return nil, err`) therefore does *not* overwrite the state var; the error preempts the write entirely. This is the mirror image of the park case above: success-with-yield re-encodes the flow so pre-park writes survive, whereas an error discards them. Consequence for authoring: you cannot return an error *and* persist state in the same dispatch. If a failure path must record something (a status, a partial result), the task has to succeed (`return nil`) and signal the failure through state plus `flow.Goto`, not through `err`.

**A step parks at most once per dispatch, interrupt XOR subgraph, never both and never two of the same kind.** Sequential side-trips are sequential tasks in the graph, not multiple parks in one task. The guard fires in two places: the `Flow` rejects a second park synchronously with an error from the parker; the foreman re-checks the returned flow after the task returns (trust boundary for a bypassed parker).

**No auto-merge.** The child's final state is returned to the calling task as `out`, not merged into the caller's state. Merging it in, if at all, is the calling task's job: it picks the fields it wants from `out` and sets them into its own state, with `flow.Set` or as its outputs.

**Interrupts propagate up through the subgraph chain to the root flow.** A child subgraph can call `flow.Interrupt`; the foreman walks the surgraph chain up to the root, the external awaiter of the root flow sees the interrupt with the child's payload, and `Resume` propagates back down to the leaf. The parent's calling step stays parked across the whole interrupt/resume cycle; the parent task does **not** re-run for it, only when the child completes or fails.

**Cancellation cascades the whole tree.** Cancelling a child cancels its parents. There is no "recover from a bad child" via cancel-of-child; that need is served by the failure-as-`err` path (child timeout surfaces as `err` with 408, parent does `flow.Retry`, an `OnError` route, or propagates).

**Single control signal per dispatch.** A task must set at most one of `Goto`, `Retry`, `Interrupt`, or `Subgraph`. Setting multiple fails the step.

### State Transformation Around a Subgraph

`in` scopes what crosses *into* the child; `out` scopes what comes back. If the parent and child use different field names, the calling task maps them: it builds `in` with the names the child expects, and reads `out` with the names the child wrote.

## Using LLMs in Workflows

There is exactly one way to use an LLM inside a workflow: **compose `llmapi.ChatLoop` as a subgraph**
with a *prepare* task immediately upstream and a *handle* task immediately downstream. Do not call
`llmapi.Chat` from a task body (it blocks one worker for the entire multi-turn conversation, with no
foreman persistence between turns) and do not call `llmapi.Turn` directly (it is the raw single-turn
primitive each provider microservice implements; you would be bypassing the tool-calling loop, usage
aggregation, and re-entry semantics that `ChatLoop` provides).

### The Two-Task Shape

`ChatLoop` is launched as a dynamic subgraph from a caller task. A second task downstream reads
the conversation result. The two tasks are connected by a single `AddTransition`; the subgraph is
not a graph node.

```go
func (svc *Service) MyWorkflow(ctx context.Context) (graph *workflow.Graph, err error) {
    graph = workflow.NewGraph("MyWorkflow")
    graph.SetURL("RunChat", myapi.RunChat.URL())               // calls flow.Subgraph(llmapi.ChatLoop, ...)
    graph.SetURL("HandleResponse", myapi.HandleResponse.URL()) // reads the final assistant message
    graph.AddTransition("RunChat", "HandleResponse")
    graph.AddTransition("HandleResponse", workflow.End)
    return graph, nil
}
```

Every turn (`CallLLM`, `ProcessResponse`, each `ExecuteTool`) becomes its own persisted foreman step,
so a worker crash mid-conversation resumes at the last completed step, the full transcript appears in
the audit trail, and the subgraph releases the worker between turns. No worker is ever pinned for the
whole loop.

### The *Run* Task

The run task builds the `ChatLoop` input, launches it through the typed `llmapi.NewSubgraph(flow)` client, and
adopts the conversation result on re-entry. The five input arguments are the `ChatLoop` input contract:

- `provider string` - target provider hostname (e.g. `claudellmapi.Hostname`), or `llmapi.ProviderAny` to
  auto-select a configured provider.
- `model string` - a tier alias (`llmapi.ModelDefault`, ...), a provider family alias, or a concrete model name
  from the provider's `*api` constants. Typed constants make a typo a compile error.
- `items []llmapi.Item` - the initial conversation (system prompt + user turn + any prior history the workflow
  is replaying), built with `llmapi.NewMessage(role, content).AsItem()`.
- `toolURLs []string` - canonical Microbus endpoint URLs the LLM may call (see "Exposing Tools" below). Empty or
  nil disables tool calling. `InitChat` resolves each URL to a tool schema by fetching its host's OpenAPI
  document at the start of the conversation.
- `options *llmapi.ChatOptions` - optional `MaxTokens`, `Temperature`, `MaxToolRounds`. `nil` accepts defaults.

```go
func (svc *Service) RunChat(ctx context.Context, flow *workflow.Flow, userQuestion string) (
    items []llmapi.Item, usage llmapi.Usage, err error,
) { // MARKER: RunChat
    prompt := []llmapi.Item{
        llmapi.NewMessage("system", "You are a helpful assistant.").AsItem(),
        llmapi.NewMessage("user", userQuestion).AsItem(),
    }
    toolURLs := []string{
        // canonical endpoint URLs the LLM is allowed to call - see "Exposing Tools" below.
        // e.g. calculatorapi.Arithmetic.URL(),
    }
    items, usage, yield, err := llmapi.NewSubgraph(flow).ChatLoop(ctx, llmapi.ProviderAny, llmapi.ModelDefault, prompt, toolURLs, nil)
    if err != nil {
        return nil, llmapi.Usage{}, errors.Trace(err)
    }
    if yield {
        return nil, llmapi.Usage{}, nil
    }
    return items, usage, nil
}
```

### The *Handle* Task

The handle task receives the conversation result via its typed arguments, populated by the run
task's outputs. The two fields are the `ChatLoop` output contract:

- `items []llmapi.Item` - the full conversation in turn order: the original system/user prompt, every
  assistant turn (reasoning, message and tool_call items), every tool result, and the final assistant reply
  that ended the loop. `items` is `Append`-reduced inside the subgraph; the parent receives the whole value.
- `usage llmapi.Usage` - aggregated token usage across every turn (input, output, cache-read,
  cache-write tokens, plus the resolved model and turn count).

The last assistant message in `items` is the LLM's final answer:

```go
func (svc *Service) HandleResponse(ctx context.Context, flow *workflow.Flow,
    items []llmapi.Item, usage llmapi.Usage,
) (answer string, totalTokens int, err error) { // MARKER: HandleResponse
    answer = llmapi.LastAssistantMessage(items)
    if answer == "" {
        // The loop exited mid-conversation (round limit hit, etc.); decide policy.
        return "", 0, errors.New("conversation did not end with an assistant message")
    }
    return answer, usage.InputTokens + usage.OutputTokens, nil
}
```

If the parent workflow only needs the final answer, persist that field and `flow.Del("items")`
to drop the verbose conversation history from downstream state and shrink the audit trail.

### Exposing Tools

Each entry in `toolURLs` is the canonical URL of a Microbus endpoint the LLM is allowed to call
mid-conversation, taken from the endpoint's `Def` (e.g. `calculatorapi.Arithmetic.URL()`). Typed
constants from each microservice's `*api` package make a typo a compile error and let the prepare
task concatenate URLs across multiple `*api` packages without collision. `InitChat` resolves each
URL to a tool schema by fetching its host's OpenAPI document, so the prepare task only chooses
*which* endpoints to expose, never how to describe them.

Choose the endpoint type by what the tool needs to do:

- **Functional endpoints** (`FeatureFunction` on `:443`). The default. A typed input/output function
  that performs a single, atomic, bounded-latency operation - a calculator, a DB lookup, a
  classifier, a unit converter. The LLM service dispatches the call as a direct bus request and
  returns the function's output to the next turn.
- **Workflow endpoints** (`FeatureWorkflow` on `:428`). Use when the tool itself needs the foreman
  machinery: bounded retries on transient failures (`flow.Retry`), error routing to a fallback
  task (`AddTransitionOnError`), per-step time budgets, a multi-step sequence, or a nested
  subgraph. The LLM service dispatches the call as a **dynamic subgraph**, so every step inside the
  tool's workflow appears in the parent flow's audit trail and re-entry/replay works the same as
  for any other subgraph. Reach for this when "the tool sometimes fails and the LLM shouldn't see
  the failure" or "the tool itself orchestrates multiple steps."

Only `FeatureFunction`, `FeatureWeb`, and `FeatureWorkflow` endpoints can be exposed as tools.
Tasks and outbound events are filtered out at the OpenAPI document level, so a URL pointing at
either is silently skipped during resolution.

Authorization for tool calls piggybacks on the calling actor: `InitChat` runs with the workflow's
actor context, so the host's OpenAPI handler omits operations the actor cannot satisfy and a tool
whose endpoint declares `requiredClaims` will simply disappear from the LLM's tool list.

When two endpoints across the supplied URLs share the same operation name, the first keeps the
bare name and subsequent ones get `_2`, `_3`, ... suffixes in argument order.

### Notes

- **The `items` boundary field.** `ChatLoop` returns the whole conversation, not just what it added. The parent
  normally gives `items` no reducer, so the run task's write replaces it, which is correct. If the parent does
  wire `items` to `ReducerAppend` and passed its history in, the run task must contribute only the new items
  (those past the prompt it sent), or the history is added twice.
- **Mocking.** Mock the underlying provider's `Turn` (`claudellm.NewMock().MockTurn(handler)`,
  etc.) rather than mocking `ChatLoop` itself - the loop logic, tool dispatch, and usage
  aggregation stay real, and the test exercises the same code path as production.

## Best Practices

A short list of high-leverage choices that emerge from operating these workflows in practice. None are enforced by the validator; they fall to the author.

**Prefer typed input/output arguments over `flow.Get` / `flow.Set`.** The task signature *is* the state contract - the marshaler binds inputs from state on entry and writes outputs back on exit, mocks get typed handlers, and a reader sees what the task reads and produces without scanning the body. Reach for `flow.Get` / `flow.Set` only when a key's name is dynamic, or when the value's type is internal to the microservice (not part of the API package and not worth promoting). The output `Out` suffix convention covers the read-modify-write case (`counter` in, `counterOut` out, both mapped to state key `counter`).

**Use `flow.Del` / `flow.Clear` to drop state the rest of the flow does not need.** LLM responses, parsed documents, raw API bodies, image bytes - anything a task consumes once and would otherwise ride through every downstream step's persisted snapshot and bloat both the wire and the audit trail. Two primitives compose for any cleanup pattern:

- `flow.Del(names...)` - drop the listed fields (variadic; mirrors `delete(m, k)`).
- `flow.Clear()` - drop every field (mirrors `clear(m)`); useful in a task that is about to populate a fresh subgraph input from scratch.

To rename a field across a contract boundary, snapshot before clearing and re-set what should survive under its new name:

```go
snap := flow.Snapshot()
var messages []llmapi.Item
snap.Get("messages", &messages)
flow.Clear()
flow.Set("conversation", messages)
```

`flow.Snapshot()` returns a `workflow.State`, a decoded copy of the state that is unaffected by the subsequent `Clear`, so the read side of the rename is safe to do in either order. A plain "keep only these" is the same shape without the rename, or just `flow.Del` of the fields that should go.

Both record JSON null in the step's changes for dropped fields, so the cleanup is preserved in the audit trail. A dropped field is removed from the state, reduced or not: `Del` is `Overwrite` with nil, which replaces a reduced field rather than contributing to it. Inside a fan-out branch a `Del` or `Clear` of a reduced field fails the step, so drop reduced fields before the fan-out or after its fan-in. None of these methods are restricted to boundaries - call them mid-flow whenever a field has served its purpose.

**Prefer `Switch` > `When` > `Goto` for branching.** `AddTransitionSwitch` (first-match-wins, validator-enforced mutual exclusivity, no `SetFanIn` needed) is the right tool for any routing where exactly one branch should run. Drop to `AddTransitionWhen` only when you genuinely want parallel branches firing under independent predicates - `When` is fan-out, not routing, and two `When` predicates intended to be mutually exclusive should be a `Switch` instead. Reserve `AddTransitionGoto` for runtime loops the task body must decide (fan-in looping back, "ask for more info then retry"). See [Switch Transitions](#switch-transitions) for the full rationale and validation rules.

**Tasks that fire external side effects must be idempotent.** `flow.Retry`, foreman lease-recovery after a worker dies mid-step, and Subgraph re-entry all replay the task body from the top. A task that charges a card, sends an email, or writes to a non-transactional store must either carry its own dedupe key (per-flow idempotency id, per-step natural key) or check first whether the effect has already happened. The framework does not deduplicate side effects for you. Tasks that are pure computation over state need no special treatment - replay just recomputes the same output.

## Time Budgets and Long-Running Work

Each task step has an execution time budget enforced by the foreman as an HTTP call timeout. The foreman's `TimeBudget` config is the hard ceiling applied to every task dispatch: it defaults to `2m`, and its validation rejects anything outside `1s`-`15m`. A task endpoint declares its own, shorter budget on its subscription with the framework option `sub.TimeBudget(duration)`; the connector then shortens that task handler's context deadline to the smaller of the caller-provided budget and the declared one, so the task is cancelled at its declared bound. The budget is a property of the task endpoint, not of the workflow graph - the graph carries no timing.

If a task exceeds its budget, the foreman cancels the HTTP call, and once the step's lease expires the engine recovers the step and runs it again. A task that intrinsically needs more than 15 minutes to finish must not block the worker - instead, use one of the two patterns below to free the worker between work and completion.

### Pattern 1: Interrupt and External Resume

Use when some external signal will indicate completion (a callback from an async service, a webhook arrival, human approval). The task triggers the long-running operation, then calls `flow.Interrupt(payload, &resume)` and returns while `yield` is true. The worker is freed immediately and the flow parks in `interrupted` status. Some other process (an inbound event sink, a webhook handler, a UI action) calls `foremanapi.Resume(flowKey, data)` when the operation completes; the task then runs again from the top, and `flow.Interrupt` returns `yield=false` with `data` unmarshaled into `&resume`. The resume data is not merged into the state.

```go
func (svc *Service) WaitForApproval(ctx context.Context, flow *workflow.Flow, requestID string) (approved bool, err error) {
    // The code before the park runs on every dispatch, so the request must be idempotent
    err = svc.sendApprovalRequest(ctx, requestID)
    if err != nil {
        return false, errors.Trace(err)
    }
    var resume struct {
        Approved bool `json:"approved"`
    }
    yield, err := flow.Interrupt(map[string]any{"requestID": requestID}, &resume)
    if err != nil || yield {
        return false, err
    }
    return resume.Approved, nil
}
```

This pattern assumes another process exists that knows when to call `Resume`. Wait time is unbounded - could be seconds or weeks.

### Pattern 2: Polling with Sleep and Retry

Use when no external trigger exists and the task must check for completion itself (waiting on a job ID, a batch import, a slow third-party API). The polling task checks completion; if not done, it calls `flow.Retry` (with backoff) and returns; if done, it returns the result. Each polling cycle is a fresh task execution, so the worker is freed between checks rather than blocking inside `time.Sleep`.

```go
func (svc *Service) PollJobStatus(ctx context.Context, flow *workflow.Flow, jobID string) (jobResult string, err error) {
    status, result, err := svc.checkJobStatus(ctx, jobID)
    if err != nil {
        return "", errors.Trace(err)
    }
    switch status {
    case "running":
        // Not done yet - schedule another poll. The give-up horizon bounds total wait.
        if !flow.Retry(30*time.Second, 1.0, 0, time.Hour) { // poll every 30s, give up after 1h
            return "", errors.New("job did not complete within poll budget")
        }
        return "", nil // Retry returned true; foreman will re-run this task after the delay.
    case "failed":
        return "", errors.New("job failed")
    default:
        return result, nil
    }
}
```

`flow.Retry(initialDelay, delayMultiplier, maxIntervalDelay, giveUpAfter)` is bounded by **wall-clock time, not a count**: it returns true while the next attempt would still land within `giveUpAfter` of the step's creation, and false once the horizon is reached, including when the next delay alone would overshoot it. The delay before attempt N is `min(initialDelay * delayMultiplier^N, maxIntervalDelay)`: a zero `initialDelay` retries immediately, a `delayMultiplier` of 1.0 gives a fixed interval, and a zero `maxIntervalDelay` leaves it uncapped. Pass `giveUpAfter <= 0` for no horizon, and to bound by count instead, pass `0` and gate on `flow.Attempt()`. `Retry` carries no condition of its own, so the task writes the retryable predicate in the surrounding `if`; timeout-only retry is `if errors.StatusCode(err) == http.StatusRequestTimeout && flow.Retry(...)`, since both foreman-side and handler-side timeouts surface as 408.

A separate "kick off the job" task should run before the polling task in the graph, writing `jobID` into state for the poller to read. The two patterns can be combined: trigger work in one task, then either interrupt-and-resume or poll in a downstream task to await completion.

## Launching Workflows and the Foreman Boundary

**Expose durable operations as workflows.** A long-running or durable operation - one that benefits from persisted state, retries, sleeps, interrupts, or human-in-the-loop pauses - belongs in a microservice's API as a *workflow* (a graph and its tasks), not as a plain synchronous endpoint. Modeling it as a workflow is exactly what lets the operation outlive a single request, survive a worker restart, and be paused and resumed.

**Boundary rule: a workflow microservice exposes its graph(s) and tasks, nothing else.** The foreman is the execution engine, not a downstream microservice - it is to workflows what the ingress proxy is to inbound HTTP: infrastructure that stands *in front of* your code, not a dependency your code reaches down into. So the microservice that *provides* a workflow must **not** import `foremanapi` to run it, exactly as a microservice does not call the ingress proxy to serve its own endpoint. In particular, do not wrap the foreman in pass-through endpoints like `RunMyWorkflow`, `StartMyWorkflow`, `CancelMyWorkflow`, `MyWorkflowStatus`: they add a hop, hide `FlowOptions` behind a narrower surface, and pull the foreman into the provider's dependency graph for no benefit.

**The `foremanapi` dependency belongs with the triggering-event code, not the API provider.** Launching a workflow is the responsibility of whatever handles the event that should start it - a UI action, an API request, a webhook, a cron ticker, an inbound event - and that code is where the `foremanapi.Run`/`Create` call is correct. Usually it lives in a *different* microservice from the one providing the workflow, which keeps the provider's dependency graph clean. It may live in the *same* microservice when that service genuinely owns the trigger - e.g. it hosts the UI layer or the ticker that starts the flow - which is an acceptable shortcut for a self-contained service with no upstream callers, though moving the triggering code to its own microservice is cleaner. The line is triggering-code vs. provider, **not** own-workflow vs. another's: exposing a synchronous endpoint that internally `foremanapi.Run`s a workflow (its own or another microservice's) to return a result is the anti-pattern, because it is precisely what drags the foreman into an API provider's dependencies. If a provider must offer a synchronous variant of logic that also runs as a workflow task, factor the logic into a plain Go helper that both the synchronous handler and the task body call - do not have the synchronous endpoint launch the flow.

**To call another unit of work from inside a task body, use a subgraph, not the foreman.** `otherapi.NewSubgraph(flow).OtherWorkflow(ctx, args...)` embeds a whole workflow as a child flow (or the raw `flow.Subgraph` for dynamic dispatch). A bare task is not independently invocable; to run one unit of work in isolation, declare a one-node workflow and subgraph it. Do **not** call `foremanapi.NewClient(svc).Run`, nor the **test-only** `Executor`, from a task body: that spawns a separate flow and forfeits re-entry, single-flow audit trail, cascading cancellation, and interrupt propagation. (The `Executor` carries a `service.Publisher` and exists only to drive endpoints from tests.)

**Whoever launches a workflow must expect it to outlive a synchronous operation.** A flow's timeline is open-ended - parks, retries, sleeps, human-in-the-loop - so a launcher that `Await`s completion must handle the await timing out while the flow keeps running detached: return a "still running" handle to poll later, an error, or issue a compensating cancel; never assume in-budget completion. The foreman fires no stop-notification event; the two ways to learn a flow's outcome (block on `Await`, or compose the follow-up as durable tasks in the workflow) are covered in Detecting Flow Completion below.

## Running Workflows

The Foreman core service orchestrates workflow execution. Use `foremanapi.NewClient(svc)` to interact with it:

```go
import "github.com/microbus-io/fabric/coreservices/foreman/foremanapi"

// Run a workflow synchronously (create-and-run + await). Returns a *workflow.FlowOutcome with
// Status, State, plus the populated side-channel for terminal/parked statuses (Error when
// Status="failed", InterruptPayload when Status="interrupted", TerminateReason when Status="terminated",
// CancelReason when Status="cancelled").
// The Go-level err is for transport/foreman/timeout failures only; a workflow that fails surfaces
// as outcome.Status == "failed" with outcome.Error populated.
outcome, err := foremanapi.NewClient(svc).Run(ctx, myworkflowapi.MyWorkflow.URL(), initialState, nil)

// Fine-grained control: Create auto-runs and returns the running flow's key; there is no separate Start.
flowID, err := foremanapi.NewClient(svc).Create(ctx, myworkflowapi.MyWorkflow.URL(), initialState, nil)
outcome, err = foremanapi.NewClient(svc).Await(ctx, flowID)

// Inspect a running flow
outcome, err := foremanapi.NewClient(svc).Snapshot(ctx, flowID)

// Cancel a flow gracefully: each in-progress step finishes, then receives the cancellation on its onError
// transition (workflow.IsCancelled tells it apart from a real failure). An interrupted flow stays interrupted.
// The reason is surfaced as outcome.CancelReason.
err = foremanapi.NewClient(svc).Cancel(ctx, flowID, "user requested")

// Terminate a running or interrupted flow and its subgraphs outright, abandoning in-flight work.
// The reason is surfaced as outcome.TerminateReason.
err = foremanapi.NewClient(svc).Terminate(ctx, flowID, "superseded")

// Resume an interrupted flow with new data
err = foremanapi.NewClient(svc).Resume(ctx, flowID, resumeData)

// Continue a thread with new input (multi-turn pattern). Returns a running flow.
// The threadKey can be any flowKey belonging to the thread; Continue finds the latest completed flow and
// inherits the thread's policy. It takes no options - use Create with Opts.ThreadKey to set policy explicitly.
newFlowID, err := foremanapi.NewClient(svc).Continue(ctx, threadKey, additionalState)
```

For typed workflow invocation in tests, use the generated `Executor` with a `WorkflowRunner`:

```go
foremanClient := foremanapi.NewClient(tester)
exec := myworkflowapi.NewExecutor(tester).WithWorkflowRunner(foremanClient)
output1, status, err := exec.MyWorkflow(ctx, input1, input2)
```

The `WorkflowRunner` interface is defined in the API package to avoid a `foremanapi` dependency. `foremanapi.Client` satisfies it implicitly.

### Flow Options (priority, fairness, delayed start)

A flow can carry scheduling hints via `*workflow.FlowOptions` (a flow-level concept, so it lives in the `workflow` package, not `foremanapi`):

```go
opts := &workflow.FlowOptions{
    Priority:       1,        // 1 to the foreman MaxPriority config (5 by default), lower runs first; 0 = unset -> the midpoint
    FairnessKey:    "tenant-42", // "" -> derived from the tid/tenant actor claim, else the "" bucket
    FairnessWeight: 2.0,      // relative dispatch share of the fairness key; 0 -> 1
    ThreadKey:      "",       // a flowKey in an existing thread to join; "" starts a fresh thread
}
outcome, err := foremanapi.NewClient(svc).Run(ctx, myworkflowapi.MyWorkflow.URL(), initialState, opts)
flowID, err := foremanapi.NewClient(svc).Create(ctx, myworkflowapi.MyWorkflow.URL(), initialState, opts)
```

`FlowOptions` authors a flow's policy **once at genesis** (`Create`/`Run`). Derived operations inherit it and take no options: `Continue` inherits the **thread's** policy, `Fork` inherits the **origin's**, and subgraphs inherit the **parent's** - choosing a derived operation *is* choosing "inherit." `Create` with `Opts.ThreadKey` is the explicit-policy escape hatch: join an existing thread while setting policy yourself. The foreman owns all defaulting; pass `nil` (or leave a field zero) to take the default. A flow that sets no priority gets the midpoint of the range (3 at the default `MaxPriority` of 5), and `Create`/`Run` reject a priority above `MaxPriority`.

There is no time-delayed start option. For a deferred start, give the workflow an entry task that calls `flow.Interrupt`; the flow rests as `interrupted` until a `Resume` releases it (the event trigger). `flow.Sleep` inside a task is the in-flow wait.

The generated per-workflow `Executor` methods keep their minimal signatures. To run a *typed* workflow with options in a test, attach them once with the `WithFlowOptions` builder:

```go
exec := myworkflowapi.NewExecutor(tester).
    WithWorkflowRunner(foremanClient).
    WithFlowOptions(&workflow.FlowOptions{Priority: 1})
output1, status, err := exec.MyWorkflow(ctx, input1, input2) // unchanged signature
```

Scheduling semantics (active): the foreman dispatches by a two-level selection over the pending steps.

- Priorities are bands that spill. The best due band is filled first, and whatever dispatch capacity it leaves
  unused goes to the next band, and so on. Priority stays strict over capacity: worse work gets only what better
  work leaves unused, with no aging, so a stream of higher-priority flows that saturates the workers starves a
  lower-priority flow for as long as it lasts. Use priority only for genuine urgency tiers, not as a soft hint.
- Within the chosen priority band, a fairness key is picked by weighted random (share proportional to
  `FairnessWeight`), then that key's oldest due step runs. The pick is re-rolled per dispatch, so expected
  throughput per key tracks its weight regardless of how deep each key has backlogged - a heavy key cannot
  monopolize a light one. Order within a single key is strict FIFO by creation.
- A key dispatches at the lowest `FairnessWeight` among its due work, so give each key one weight; a flow created
  with a smaller weight for the same key lowers the key's share while it has due work.

Relevant `foreman.core` configs: `MaxPriority` (the number of priority levels, the same on every replica), `Workers` (the
maximum number of workers executing steps on each replica; left at -1, the engine derives it), and `TimeBudget` (the hard per-step dispatch
ceiling; a task may declare a shorter `sub.TimeBudget` of its own).

## Detecting Flow Completion

The foreman has **no stop-notification event** - there is no `NotifyOnStop` option and no `OnFlowStopped` event
to subscribe to (both removed). A stopped flow is not pushed anywhere; there are two ways to learn its outcome,
suited to different situations:

1. **`Await`** - block a live caller until the flow stops, then read the outcome.
2. **Orchestration** - model the follow-up work as tasks inside a workflow that calls the real work as a
   subgraph, so the reaction to success or failure is itself a durable, retryable step.

Pick `Await` when a caller is standing by for the result. Pick orchestration when the reaction must happen
reliably regardless of who is (or isn't) waiting: a push notification, a downstream call, a compensation.

### Await

```go
outcome, err := foremanapi.NewClient(svc).Await(ctx, flowKey)
```

`Await` blocks until the flow stops (`completed`/`failed`/`cancelled`/`interrupted`) and returns the
`*workflow.FlowOutcome`. It wakes on a status-change signal, not polling.

Good for a request/response caller that holds the flowKey and can wait, tests, and short flows. Its limits are
inherent to bridging an open-ended flow to a synchronous caller:

- The caller must stay alive and connected. If its context deadline fires before the flow stops, `Await` returns
  without the outcome; the flow keeps running and the caller must `Await` again (it still holds the key).
  Long-running or human-in-the-loop flows routinely outlive a request context.
- It does not survive the caller process restarting - there is no durable "call me back".
- It is a poor fit for fire-and-forget submissions, where nobody waits.

### Orchestration (recommended for reliable follow-up)

Wrap the real work in an orchestrating graph: one task launches it as a subgraph, and separate tasks handle the
success and failure paths. Because each follow-up is its own step, it is checkpointed and retried independently -
a delivery that must not be lost belongs here, not in a caller's `Await`.

```go
graph.SetURL("CallSubgraph", myapi.CallSubgraph.URL())
graph.SetURL("OnSuccess", myapi.OnSuccess.URL())
graph.SetURL("OnFailure", myapi.OnFailure.URL())
graph.AddTransition("CallSubgraph", "OnSuccess")        // normal path
graph.AddTransitionOnError("CallSubgraph", "OnFailure")  // error path
graph.AddTransition("OnSuccess", workflow.End)
graph.AddTransition("OnFailure", workflow.End)
```

- **CallSubgraph** runs the child via `flow.Subgraph` (or the typed `xapi.NewSubgraph(flow)`), yields while it
  runs, and returns any error so the graph routes it to OnFailure via the error transition.
- **OnSuccess** runs on the normal transition. Do the follow-up work here; because it is its own step it can
  retry itself with `flow.Retry` (e.g. re-attempt a web notification with backoff until it lands within a
  bounded horizon).
- **OnFailure**, wired with `AddTransitionOnError`, has the error in the `onErr` state field (input
  `onErr *errors.TracedError`) and can notify, compensate, or clean up, again as a retryable step of its own.

Splitting the follow-up into its own task is what makes it durable: a crash between the subgraph completing and
the notification being delivered is recovered like any other step, and the delivery is not tied to a caller
staying connected. Doing the follow-up inside CallSubgraph instead would couple it to the subgraph call's own
attempt and lose that independent retry. This is the guaranteed-delivery replacement for the removed best-effort
stop event.

**Interrupts are not a terminal outcome.** The orchestrator observes the subgraph's terminal outcome (success or
failure); it cannot react to the subgraph *interrupting*, because an interrupt parks the whole chain including
the orchestrator's CallSubgraph step, so no task runs at that moment. To notify that a flow is *waiting for
input*, put a notify task *before* the interrupting step: the task that is about to `flow.Interrupt` knows it is
about to wait, so it (or a step just ahead of it) reports "pending" first.

## Debugging Workflows

- `foremanapi.NewClient(svc).History(ctx, flowID)` - step-by-step execution trace with state snapshots and nested subgraph history
- `foremanapi.NewClient(svc).Fork(ctx, stepKey, stateOverrides)` - clone a terminal flow's prefix up to the chosen step into a new self-contained flow and re-run from there with modified state, inheriting the origin's scheduling/baggage. The original flow is immutable; Fork never mutates it. A terminal flow is recovered only by forking, not by an in-place restart.

## Mocking Workflows

Workflows can be mocked at two levels of fidelity. Both require the **real foreman** in the test app.

**Tier 1: Workflow-level mock (common case)** - Collapses the entire workflow into a single synthetic task. The handler receives the `*workflow.Flow` carrier with access to state and control signals:

```go
creditflowMock := creditflow.NewMock()
creditflowMock.MockCreditApproval(func(ctx context.Context, flow *workflow.Flow, applicant creditflowapi.Applicant, faultInjection string) (approved bool, creditVerified bool, employmentFailures int, identityVerified bool, err error) {
	return true, true, 0, true, nil
})

app := application.New()
app.Add(svc, foreman.NewService(), creditflowMock, tester)
app.RunInTest(t)
```

Under the hood, `MockCreditApproval` overrides the graph endpoint to return a trivial single-task graph and subscribes a synthetic task handler on the mock. Pass `nil` to clear the mock.

**Tier 2: Individual task mocks (rare case)** - For fine-grained control over specific tasks (interrupt/resume, per-step assertions), mock individual task endpoints while letting the real graph drive execution:

```go
creditflowMock := creditflow.NewMock()
creditflowMock.MockVerifyCredit(func(ctx context.Context, flow *workflow.Flow, creditScore int, faultInjection string) (creditVerified bool, err error) {
	return true, nil
})
```
