# SQL-Backed Microservices

## Instructions for Agents

Read this file before adding a SQL database to a microservice, or working on a microservice that has one.

A SQL-backed microservice keeps its data in a SQL database through the
[sequel](https://github.com/microbus-io/sequel) package, a thin layer over `database/sql` that gives MySQL, MariaDB,
PostgreSQL, CockroachDB, SQL Server and SQLite one API. This file covers how sequel plugs into a Microbus
microservice and the patterns that work well. For sequel's full API, read its own docs in the local Go module
cache:

```bash
ver=$(go list -m -f '{{.Version}}' github.com/microbus-io/sequel)
cat "$(go env GOMODCACHE)/github.com/microbus-io/sequel@$ver/README.md"
```

`exampleservices/yellowpages` in the Microbus repository is a small, complete example.

## Endpoints Wrap the SQL Directly

A microservice's endpoints are the abstraction over its persistence. Each endpoint runs its SQL statements itself;
no further layer (a repository, a DAO, an ORM) is needed. The microservice boundary already hides the database from
the rest of the application, so another layer only adds indirection. Small private helpers that several endpoints
share, such as one that scans a row into a struct, are fine.

## Opening, Migrating and Closing the Database

Add a secret config for the data source name, typically `SQLDataSourceName`, and hold the database in the
`Service` struct:

```go
type Service struct {
	*Intermediate // IMPORTANT: Do not remove

	db *sequel.DB
}
```

Open the database and apply its migrations in `OnStartup`, and close it in `OnShutdown`:

```go
func (svc *Service) OnStartup(ctx context.Context) (err error) {
	dataSourceName := svc.SQLDataSourceName()
	if dataSourceName == "" && svc.Deployment() == connector.LOCAL {
		dataSourceName = "file:local.sqlite"
	}
	if svc.Deployment() == connector.TESTING {
		// An isolated database per test, shared by the replicas of one test app
		dataSourceName, err = sequel.CreateTestingDatabase("", dataSourceName, svc.Plane())
		if err != nil {
			return errors.Trace(err)
		}
	}
	svc.db, err = sequel.OpenSingleton("", dataSourceName) // The driver is inferred from the data source name
	if err != nil {
		return errors.Trace(err)
	}
	// Route sequel's spans, metrics and migration logs through the connector
	svc.db.SetTracerProvider(svc.TracerProvider())
	svc.db.SetMeterProvider(svc.MeterProvider())
	svc.db.SetLogger(svc.Logger())
	migrations, err := fs.Sub(svc.ResFS(), "sql")
	if err != nil {
		return errors.Trace(err)
	}
	err = svc.db.Migrate("myservice", migrations) // A name unique to this microservice; never change it
	return errors.Trace(err)
}

func (svc *Service) OnShutdown(ctx context.Context) (err error) {
	if svc.db != nil {
		err = svc.db.Close()
	}
	return errors.Trace(err)
}
```

- **LOCAL** falls back to a SQLite file in the working directory when no data source name is configured, so the
  microservice runs on a developer's machine with no database server.
- **TESTING** gets its own database from `sequel.CreateTestingDatabase`, keyed by the plane. Tests run in parallel
  without seeing each other's rows, while the replicas of one test app share a database. With no data source name
  configured, the testing database is SQLite, unless the `SEQUEL_TESTING_DSN` environment variable names a server;
  with one, it is created on that server and dropped once every handle on it has closed.
- **Telemetry.** Without the three `Set` calls, sequel's spans and `sequel_*` metrics never reach the connector, and
  the sequel Grafana dashboard stays empty.
- **`OpenSingleton`** returns one shared `*sequel.DB` per data source name within the process, sizing its connection
  pool to the number of openers, which suits several microservices of one app that use the same database.
- **The migration sequence name** records which migrations have run on a database. Changing it makes sequel run them
  all again.

Tests do not read `config.local.yaml`, so the config does not reach them. To run tests against a real database
server instead of SQLite, set the `SEQUEL_TESTING_DSN` environment variable to a base data source name that names no
database, in `env.local.yaml` at the root of the project (git-ignored) or in the shell. Each test app then gets its
own database on that server. If tests fail to connect, ask the user for the credentials.

```yaml
SEQUEL_TESTING_DSN: root:root@tcp(127.0.0.1:3306)/
```

Base data source names per database: `root:root@tcp(127.0.0.1:3306)/` (MySQL),
`mariadb://root:root@tcp(127.0.0.1:3306)/` (MariaDB), `postgres://postgres:postgres@127.0.0.1:5432/` (PostgreSQL),
`sqlserver://sa:sa@127.0.0.1:1433` (SQL Server).

To run the application locally against a database server instead of the SQLite file, set the microservice's data
source name, including the database, in `config.local.yaml`:

```yaml
myservice.example:
  SQLDataSourceName: root:root@tcp(127.0.0.1:3306)/myservice
```

## Migrations

The schema is created and evolved by migration files placed in the `sql` subdirectory of the microservice's
`resources` directory, for example `myservice/resources/sql/1.sql`. The microservice's `resources/embed.go`
(`//go:embed *`) embeds them into the binary along with its other resources, and `OnStartup` hands that
subdirectory to `Migrate` through `fs.Sub(svc.ResFS(), "sql")`. Name the files by number (`1.sql`, `2.sql`, ...);
they run in numeric order, each once per database. Separate the statements in a file with a `;` at the end of a
line. A `-- DRIVER:` line applies to the one statement that follows it.

- **Never edit a migration that has shipped.** Add the next number instead, even to undo a change: find the largest
  number in `resources/sql` and add one.
- **Support the databases the project deploys to**, plus SQLite if it uses the LOCAL and TESTING fallbacks. Mark a
  statement that differs between databases with a `-- DRIVER:` line naming the drivers it applies to: `mysql`,
  `mariadb`, `pgx` (PostgreSQL), `cockroachdb`, `mssql` (SQL Server) or `sqlite`. A statement that suits several
  lists them all, as in `-- DRIVER: mysql mariadb`.
- **Give time columns millisecond precision** to match `NOW_UTC()`: `DATETIME(3)` on MySQL and MariaDB,
  `TIMESTAMP(3)` on PostgreSQL, `DATETIME2(3)` on SQL Server, `DATETIME` on SQLite. A plain `DATETIME` on MySQL has
  no fractional digits.
- Use snake_case for tables, columns and indexes, and uppercase SQL keywords. SQLite accepts only one column per
  `ALTER TABLE`.

```sql
-- DRIVER: mysql mariadb
ALTER TABLE persons ADD nickname VARCHAR(64) NOT NULL DEFAULT '';

-- DRIVER: pgx cockroachdb
ALTER TABLE persons ADD COLUMN nickname VARCHAR(64) NOT NULL DEFAULT '';

-- DRIVER: mssql
ALTER TABLE persons ADD nickname NVARCHAR(64) NOT NULL DEFAULT '';

-- DRIVER: sqlite
ALTER TABLE persons ADD COLUMN nickname TEXT NOT NULL DEFAULT '';
```

## Writing Queries

- **Bind every value as a `?` parameter**; never build SQL from input. sequel rewrites `?` into each driver's
  placeholder.
- **Use sequel's virtual functions** where databases differ: `NOW_UTC()`, `DATE_ADD_MILLIS(expr, ms)`,
  `DATE_DIFF_MILLIS(a, b)`, `LIMIT_OFFSET(limit, offset)` and `REGEXP_TEXT_SEARCH(? IN col1, col2)`.
- **Use the database's clock** (`NOW_UTC()`) for created and updated times, so times agree across replicas, and keep
  times in UTC.
- **Get a new row's ID with `svc.db.InsertReturnID(ctx, "id", stmt, args...)`**, which works on every driver.
- **NULL:** write a Go zero value as `NULL` with `sequel.Nullify(value)`. Read a nullable column into a plain field
  with `sequel.Nullable(&field)`, then call `sequel.ApplyBindings(args...)` after the scan.
- **Order every paged query by a unique column.** `LIMIT_OFFSET` needs an `ORDER BY`, and times are whole
  milliseconds, so ordering by a time alone can skip or repeat rows across pages. Add the ID as a tie-breaker.
- **Filters:** a zero-valued filter adds no condition, so an empty query selects everything. An empty list filter
  selects nothing (`1=0`), not everything.
- **Transactions:** `svc.db.Transact(ctx, func(tx *sequel.Tx) error {...})` runs a closure in a transaction and
  retries it on a deadlock or lock contention.
- **Rows affected:** MySQL and MariaDB report the rows an `UPDATE` changed, not the rows it matched, so an update
  that changes nothing reports zero rows. Do not take zero to mean "not found" there without checking.

## Exposing the Data: JSON and REST Endpoints

A SQL-backed microservice can expose its data in either style, or both:

- **JSON (RPC-style) functional endpoints**, such as `Create(ctx, person) (key, err)` and
  `Load(ctx, key) (person, found, err)`, with typed In/Out structs, called through the generated client by other
  microservices. The natural choice for data used inside the application.
- **REST endpoints**, with resource routes and HTTP verbs (`POST /persons`, `GET /persons/{key}`,
  `PUT /persons/{key}`, `DELETE /persons/{key}`, `GET /persons`), built on the magic `httpRequestBody`,
  `httpResponseBody` and `httpStatusCode` arguments, so the body is the object itself and the status code carries
  the outcome. The natural choice for an API consumed outside the application.

When a microservice offers both, the REST endpoints are thin wrappers that call the JSON endpoints' handlers and
translate the result into HTTP terms, so the SQL lives in one place:

```go
func (svc *Service) LoadREST(ctx context.Context, key int) (httpResponseBody *myserviceapi.Person, httpStatusCode int, err error) { // MARKER: LoadREST
	person, found, err := svc.Load(ctx, key)
	if err != nil {
		return nil, 0, errors.Trace(err)
	}
	if !found {
		return nil, http.StatusNotFound, nil
	}
	return person, http.StatusOK, nil
}
```

- **A missing row is an outcome, not an error.** Return `found`, `stored` or `deleted` from the JSON endpoints rather
  than a 404 error: every error an endpoint returns is logged as one. The REST endpoints turn them into 404s.
- **Status codes:** 201 on create, 200 with a body on read, 204 on update and delete, 404 when missing, and 409 when
  a conditional update loses to a newer revision (see below). Invalid input is already a 400 from `dv8` validation.
- **Choose each endpoint's exposure.** An endpoint on `:443` is the data API, reachable through the ingress; gate it
  with `requiredClaims`. An endpoint meant only for other microservices goes on `:444`.

## Recommended Patterns

### No Foreign Keys or JOINs Across Microservices

A microservice's tables are its private implementation, even when several microservices share one database. No
microservice may define a foreign key to, or `JOIN` with, another microservice's tables, nor rely on how they are
laid out. A microservice that needs another's data picks one of three strategies:

- **On-demand querying** - call the other microservice's endpoints, preferably bulk ones, when the data is needed.
  Always consistent, at the cost of a round trip.
- **Caching** - keep the other microservice's objects in a cache (for example `svc.DistribCache`), invalidated by its
  events.
- **Denormalization** - copy the needed columns into this microservice's own table, kept current by the other
  microservice's events. Enables local `JOIN`s and filtering.

| Strategy | Consistency | Latency | Storage |
|---|---|---|---|
| On-demand querying | Strong | Higher (round trip) | None |
| Caching | Eventual | Low (cache hit) | Volatile (memory) |
| Denormalization | Eventual | None (local query) | Durable (database) |

Data that never changes needs no invalidation. A ticker can refresh a cache or a copy on a schedule, instead of or
alongside events.

### Multi-Tenancy

When the data is multi-tenant, add a tenant column and gate every statement on the caller's tenant
(`tid, _ := frame.Of(ctx).Tenant()`), reads, updates and deletes alike. Make the tenant column the first column of
the primary key and of every composite index, so each tenant's rows and index entries stay together. A table shared
by all tenants uses tenant `0`.

### Revisions

When concurrent writers may update the same row, add a `revision` column, increment it on every update
(`revision=revision+1`), and offer a conditional update that adds `AND revision=?` with the caller's copy. If
another writer updated the row in the meantime, the revision has moved on and the update matches no row: report a
409 rather than overwriting the newer data.

### Events

Fire outbound events when objects are created, updated and deleted (for example `OnPersonCreated`), carrying the
keys. They are what let other microservices cache or copy the data.

### Bulk Endpoints

Offer bulk endpoints (`BulkLoad`, `BulkDelete`, ...) so callers do not loop over single calls (1+N round trips).
Split a large batch across statements within the database's limits: SQL Server allows at most 2,100 parameters per
statement.

### Opaque Keys

A sequential ID reveals how many rows a table has. When that matters, expose keys in a form that hides it, such as
an encrypted ID, and keep the integer inside the microservice.

### Reservations

To let workers claim rows without holding locks, add a `reserved_before` time column. A worker reserves a row with
an update that sets `reserved_before=DATE_ADD_MILLIS(NOW_UTC(), ?)` only where `reserved_before<=NOW_UTC()`, and
the reservation lapses on its own if the worker dies.
